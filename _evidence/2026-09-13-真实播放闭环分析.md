## 一句话结论

**闭环在真实播放中确实触发了（3 次降档 + 2 次回升），但暴露了一个此前完全没发现的缺陷：
换档本身会触发 libplacebo 重新编译 shader（最慢一次 1199.7 ms），编译期的丢帧被脚本当成
「还在卡」，于是刚回升就复发 —— 形成 full ⇄ emergency 的振荡。**

> **处置**：根因已定位，修复已落地（脚本 **v5.7** 新增换档/起播静默期），回归测试通过。
> 详见「五之二、已实施的修复」。⚠ 但尚未在真实渲染路径上复验。

## 三、五个发现

### 发现 1 ✅ 闭环确实工作（首次真实负载实证）

`full → emergency` 的降档判定在真实播放中触发了 3 次，触发时脚本记录的瞬时丢帧率分别是
**2.0/s、5.64/s、6.64/s**。这比上一轮用 IPC 发 `set speed 8` 人为压出的 159.9/s 小两个数量级，
但**真的越过了 `DROP_THRESHOLD=1.0` + `CONFIRM=2` 的门槛**。

> 意义：阈值量级「不离谱」这一点，现在有真实数据支撑了（此前只有人为负载）。

### 发现 2 ⚠️ 换档会「自伤」—— 降档瞬间反而狂丢帧（本轮最重要）

把档位变更和 shader 编译日志对齐，因果链清清楚楚：

| 时间 | 事件 |
|---|---|
| `33.833` | `AUTO-QUALITY -> emergency (丢帧2.0/s)` ← 换档 |
| `34.131` | `Spent 274.210 ms translating GLSL to SPIR-V (slow!)` |
| `35.345` | `Spent 1199.704 ms translating HLSL to DXBC (slow!)` ← **1.2 秒停滞** |
| `36.603` | `Spent 208.870 ms translating GLSL to SPIR-V (slow!)` |
| `37.491` | `Spent 876.862 ms translating HLSL to DXBC (slow!)` |
| `36.649` | 采样：`drops=42`（9.96/s） ← 编译期丢的 |
| `39.684` | 采样：`drops=92`（16.63/s） ← 编译期丢的 |
| `42.667` | 采样：`drops=0`（**-30.54/s**） ← 编译完成、计数器归零 |

**降档后 34~42 秒这 8 秒里丢了 134 帧，全部来自换档引发的 shader 重编译，与「片源喂不动」无关。**

机制：`mpv` 的 `--gpu-shader-cache` **默认就是 `yes`**（`mpv --list-options` 实测 `Flag (default: yes)`），
所以**同一个** shader 重跑极快 —— 日志里 33.671s 那批只花 8.7 ms，就是缓存命中。
但换档把 `scale` 从 `ewa_lanczossharp` 换成 `fast_bilinear`，这是**一个此前从未编译过的 shader 变体**，
缓存无从命中，只能现场把 GLSL → SPIR-V → HLSL → DXBC 走一遍，实测最慢一次 **1199.704 ms**。

> 所以「给 libplacebo 配缓存」这条路**走不通** —— 缓存早就开着，它救不了「换档必然引入新 shader」这件事。

### 发现 3 ⚠️ 于是产生振荡（flapping）

把发现 2 代进状态机：

```
emergency 档稳定 60s（丢帧全 0）
  → CLEAN_SECONDS 满足 → 回升 full
  → full 档重型 shader（ewa_lanczossharp + deband）重新编译
  → 编译期丢帧 → 立刻越过阈值
  → 2~3 秒内又降回 emergency
  → emergency shader 再编译 → 又丢一波
  → …循环
```

日志里 `1:40 回升 → 1:42 复发`（隔 2 秒）、`2:42 回升 → 2:45 复发`（隔 3 秒），
两次复发都远小于 `RECHECK_SECONDS=25`，**说明复发窗口还没走完就被打回去了**。

### 发现 4 ✅ 冷却机制真的生效了（v5.4 那个设计没白写）

脚本有 `fail_count >= 2 → blocked_until = now + COOLDOWN_SECONDS(300)`。
实测：`2:45` 复发后**到日志结束（3:25）再没有回升过**，正好落在 300 秒冷却窗内。

> 这是 `COOLDOWN_SECONDS` 这条路径第一次被真实触发并验证。

### 发现 5 ❓ 为什么 720p 轻片源在 full 档就丢帧（未解）

- 前 15 秒**零丢帧**（含 5.9~9.4s 的首次全量 shader 编译期）
- 15.6s 起断续丢帧：`2 / 14 / 3 / 0 / 6 / 12` 帧（每 3 秒一采样，0.66~4.67/s）
- 15~35s 区间**没有任何 seek / pause / 窗口变化事件**（已 grep 排除）
- 幅度不大，但足以在 2 个连续窗口后触发降档

**推测（[未实证]）**：这段时间系统上有别的负载（用户在同时操作电脑 / 其他程序），
CPU（i7-8550U 低压 U）或核显被抢，导致渲染侧掉帧。
若成立，则暴露第二个设计缺陷：**闭环对「与播放无关的系统负载」没有免疫力** ——
用户一边看片一边干别的，就会被误判为「解码喂不动」，然后触发降档+编译风暴。

## 四、根因归纳

闭环的两个设计缺陷，都是「换档」这个动作本身的副作用：

| # | 缺陷 | 后果 |
|---|---|---|
| A | **换档成本未计入** —— 换档触发 shader 重编译（最长 1.2s），编译期丢帧被算进 bad_streak / clean_accum | 降档后看起来「更卡」；回升后 2 秒即复发 → 振荡 |
| B | **对外部负载无免疫** —— `DROP_THRESHOLD=1.0/s` 太低，系统瞬时负载造成的轻微丢帧也会触发降档 | 用户边看边干活时，无谓降档 + 编译风暴 |

另外一条**观测缺陷**：换档重建 filter chain 会让 `frame-drop-count` 归零，
产生 `-30.54/s` 这类负值。负值不会被判成 stutter（算是运气好），但它**掩盖了编译期的真实丢帧**，
使「换档后是否真的变好」无法从采样里读出来。

## 五、修复建议

### 建议 1（对症，最小改动）✅ 已实施：换档后加「静默期」

换档后 N 秒内，采样只记录、不参与 bad_streak / clean_accum 判定。
N 取值要覆盖最长编译时间 × 余量：实测最慢 1199.7 ms，建议 **N = 6~8 秒**。

```lua
-- 新增
local SETTLE_SECONDS = 8          -- 换档后静默期: 覆盖 shader 重编译(实测最慢 1.2s)×余量
local settle_until = 0

-- enter() 里设置
settle_until = mp.get_time() + SETTLE_SECONDS

-- on_tick() 判定前插入
if now < settle_until then
  prev_drops, prev_time = drops, now   -- 只推进基准, 不计入 streak
  return
end
```

### 建议 2：把阈值从「率」改成「率 + 绝对量」

单纯提高 `DROP_THRESHOLD` 会让真实卡顿漏判。建议改成双条件：

```lua
local DROP_THRESHOLD = 3.0        -- 从 1.0 提高: 3 秒窗口内 ≥3 帧/s 才算卡
local MIN_DROPS      = 10         -- 且该窗口绝对丢帧 ≥10 帧(过滤瞬时毛刺/外部负载)
...
local stutter = (rate > DROP_THRESHOLD) and ((drops - prev_drops) >= MIN_DROPS)
```

真实触发时的数据是 2.0 / 5.64 / 6.64 帧/s —— 提高阈值到 3.0 后仍能抓住后两次，
第一次（2.0/s）会漏掉。要不要漏掉它取决于用户对人眼可感卡顿的容忍度，建议实测后定。

### 建议 3：升档更保守

`CLEAN_SECONDS` 60 → 120，或要求「连续 2 个 60s 窗口零丢帧」才试探回升，
让回升决策不那么容易被一次编译风暴推翻。

### ~~建议 4：给 libplacebo 配 shader 缓存~~ ❌ 此路不通

原本以为没配缓存，实测 `mpv --list-options` 显示 `--gpu-shader-cache` **默认就是 `yes`**。
缓存只能省「重复编译同一个 shader」，而换档引入的是**新 shader 变体**，必须现场编译 —— 缓存救不了。
**真正的出路只有建议 1 的静默期**：既然编译躲不掉，就把它从判定里排除掉。

## 五之二、已实施的修复（v5.7）

**建议 1 已落地**，脚本升到 **v5.7**，新增 `SETTLE_SECONDS = 10`：

- `enter()`（换档）与 `file-loaded`（起播）都会设置 `settle_until = now + SETTLE_SECONDS`
- `on_tick()` 在静默期内**只记录采样、不参与判定**（`prev_drops` 仍推进，所以静默期一结束就能拿到正确的 3 秒增量）
- 取值依据：日志显示「换档 → 编译 → 计数器归零」约需 9 秒（33.8s → 42.7s），取 10 留余量
- 副作用（已知、可接受）：真实卡顿的响应延迟 +10 秒（总响应 ≈ 10s 静默 + 6s 确认）

**验证**（`tools/loop_test.py` 回归 + 单次加载实测）：

```
 0.188  AUTO-QUALITY -> full (新片源 width=1280)
 3.032  settle 7.2s left, skip judgement (rate=0.00/s drops=0 tier=full)
 6.032  settle 4.2s left, skip judgement (rate=0.00/s drops=0 tier=full)
 9.032  settle 1.2s left, skip judgement (rate=6.00/s drops=18 tier=full)   ← 加压已开始，被正确跳过
12.032  sample rate=3.33/s drops=28 stutter=true                           ← 静默期结束，开始判定
```

回归结论：**降档 ✅ 通过 / 回升 ✅ 通过** —— 静默期消除了振荡燃料，但没有破坏闭环本身。

⚠ 静默期**尚未在真实渲染路径（`gpu-next` + 真实 shader 编译）上复验** —— 上面的回归用 `--vo=null`，
编译开销被绕过了。需要在下次真实播放时用 `logcheck.py` 确认「换档后不再出现 `回升后复发`」。

## 六、方法论教训（给未来的自己）

**上一轮用 IPC `set speed 8` 压出 159.9 帧/s 的丢帧，证明了「机制能触发」，
但完全没暴露换档成本和振荡 —— 因为人为负载是「持续、恒定」的，
而真实场景里最要命的丢帧是「换档瞬间的编译尖峰」。**

> **人工负载验证机制，真实负载验证参数。** 两者不可互相替代。
